# Proposed additive installer diagnostic context v1

Decision: one validated UUIDv4 labels an installation/update process chain from Desktop handoff through Setup/scripts and Runtime logging. Optional diagnostic metadata holds stable source-selected code/component/stage, conservative retryable=false, redacted safe_message and operation_id. It does not confer authority and cannot affect tenant/task/signed trace, lock ownership, command admission or automatic retry. It is not written to registry/journals. A Setup invocation, including manual retry, is one operation; a new Desktop update reservation creates a new ID.

Existing bootstrap channel and stage protocol machine fields, coordination versions, signatures, hashes and marker values stay unchanged. Consumers may ignore optional diagnostic metadata. Structured metadata has its own schema_version youtab.diagnostic.v1. Invalid external IDs are never emitted verbatim; standalone Setup uses a fresh ID, standalone Runtime context may be absent.

Reuse Node crypto, existing Cargo uuid/once_cell and Python uuid plus current redactors/event emitters/process env/record factory. No new dependency, broad exception system or billing-code reuse. Pending independent review, actual Node/Rust/Python tests and controlled process-chain verification; preparation does not claim completion.

R2 closes presentation IPC strings and last-chance correlation: presentation message/error strings are redacted with configured environment; null/nonstring/machine fields unchanged. JS UUID validation is exact 36 characters and stage labels reject terminal newlines. Python configured formatters use safe empty defaults for external/manual context tags; explicit gateway panic context uses the same validated helper, including safe fallback. Rust operation ID is initialized before its panic hook and panic diagnostics validate correlation without reading payload. Complete synthetic PEM fixture bytes remain runtime-constructed per unchanged secret-gate rules; current fixture bytes are preserved.

R3 also forwards the same validated operation env explicitly to the existing installed-backend health-probe command (both relocation Python and ordinary CLI serve paths), preserving private probe home/ready-file/current-directory/kill-on-drop controls. All four update/rebuild run_streamed calls use the same child_env built by update_child_env, including existing bounded retry paths; their policy and exit codes are unchanged. This is verified source wiring, not proof of a real installed process-chain/update acceptance run.

R4 uses the mandated YOUTAB_AGENT_DIAGNOSTIC_OPERATION_ID prefix. Error-only or empty-string-message progress chooses a nonempty safe message, otherwise its safe string error, preserving useful diagnostics. retryable=false means the diagnostic metadata authorizes no NEW retry; original bounded retry policy and existing user retry controls are unchanged. It is not consulted by effect/auth/lock decisions.
